## 3. 根因与修复设计

### A1：趋势摘要依赖接口返回顺序

线上 Shokz 收入从 2026-05 的 159,025.19 到 2026-10 的 59,231.86，回答给出下降约 168.5%；按起始月份计算应为下降 62.75%。

代码链路：

1. `offer_db.py:2077` 按月份倒序返回商户月度数据。
2. `agentSession.ts:1418` 直接映射响应，没有排序。
3. `agentSession.ts:755` 的 `trendSummary()` 将数组第一项视为起点、最后一项视为最新值。

固定响应按“2026-10、2026-05”传入时，当前工具返回 `first=59231.86`、`latest=159025.19`、`changeRate=1.685`。程序产生的是正 168.5%，线上文字又将它解释为下降，形成了摘要方向错误与自然语言解释错误的叠加。

**修复设计：** 在趋势工具边界统一规范月份，按时间升序排列后再计算起止、增量和变化率。摘要应携带起止月份，模型不得自行交换首末值或改写方向。展示表可以倒序，但图表和摘要使用同一份时间正序序列。

变化率使用 `(期末值 - 期初值) / 期初值`，保留小数比例；期初为零时变化率返回不可计算，不能伪造 0%。月份不足两项、指标缺失和当前月份未结束分别说明。当前月完整性依据数据期间和截至时间标记，不仅依靠模型临时判断。

### A2：EPC 公式与比较基线不一致

`agentSession.ts:353` 的单商户 `metricValues()` 优先使用源 EPC，缺少时却退回“收入 ÷ 点击”。`aggregate()` 在 `agentSession.ts:386` 始终使用“总收入 ÷ 总点击”。Report 的 `entityReports.ts:108` 与数据库 `merchant_amazon_metrics()` 使用联盟佣金口径。

线上 Tier 1 对比显示 EPC 2.261，而同表联盟佣金 23,458.86、点击 80,359，对应联盟 EPC 约为 0.292。固定数据中两个商户收入总额 1,900、联盟佣金总额 300、点击总额 200，当前汇总 EPC 为 9.5，联盟 EPC 应为 1.5。

**修复设计：** 单商户、Tier、品类、全站、趋势和对比的联盟 EPC 均使用联盟佣金口径。可复用 Report 的别名与取值逻辑；缺少源 EPC 时，只在联盟佣金和点击均可用且分母有效时计算。真实源 EPC 为零时必须保留，不能用 `epcRaw || ...` 覆盖。

金额、订单和点击的群体汇总继续表示总量；汇总 EPC 和 CVR 表示总分子除以总分母的加权指标。明确标注“Tier 汇总”“全站汇总”，不能称为商户平均值。当前没有计算商户均值或百分位时，回答不得声称某商户的总收入高于群体平均。

### A3：工具契约无法表达筛选和指定排序

线上要求“vacuum cleaner、Tier 1、CVR ≥ 5%、联盟 EPC 降序、最多 3 家”，回答将 CVR 未提供的 Lefant 认定为达标，工具表仍列出 Tier 2/3 商户。

`agent_tool_registry.py:322` 的参数只有 `keyword`、`semanticAlternatives`、`mode`、`limit`。`agentKeywordSearch.ts` 的 `searchAgentKeywords()` 没有筛选入口，调用 `compareRecommendationOffers()` 时没有传入查询排序；默认首先按销售额排序。固定数据中 Tier 2 商户仍被返回，且 EPC 为 1 的商户排在 EPC 为 2 的商户之前。

目录命中而指标缺失的商户，当前工具已经用缺失字段和 `ranked=false` 表示；“缺失仍达标”发生在综合解释中。仅加提示词不能补足工具契约缺口。

**修复设计：** 扩展现有关键词工具的受控参数，并贯穿 Python 验证、签名绑定、前端执行和综合结果投影。例如，以下是拟新增的参数形状：

```json
{
  "keyword": "vacuum cleaner",
  "mode": "recommendation",
  "tiers": ["Tier 1"],
  "metricFilters": [{ "field": "conversionRate", "operator": ">=", "value": 0.05 }],
  "metricSort": { "field": "epc", "direction": "desc" },
  "limit": 3
}
```

字段、操作符、Tier 和排序方向均使用枚举白名单；不支持的条件明确返回受控错误。执行顺序为关键词匹配、可用性检查、过滤、指定排序、截取数量，不能先截取再过滤。缺少门槛指标的商户归入“数据不足”，不计入达标结果。

结果携带已应用条件、满足条件的数量、因指标缺失排除的数量和当前匹配集合完整性。正文与结构化表均引用这份最终结果。没有达标商户时明确返回零家，不自动放宽门槛。没有指定排序时保留现有默认规则；指定 EPC 排序时按 EPC 排序，不能再暗中优先 Tier 或收入。

### A4：界面保存上下文，规划没有读取

线上“这个商户的前 5 个 ASIN”要求重新提供商户，右侧却显示 Shokz。纠错追问又被回答为“看不到刚才的对话”。

代码中存在以下断点：

- `CopilotKitAgentRuntime.vue` 将历史和记忆写入 `offerIntelligence` 状态。
- `agent_agui.py:276` 构造规划请求时只传本轮问题、语言、工具、ASIN 引用和推广摘要。
- 现代 session 的 `agentSession.ts:1030` 同样没有传商户记忆和历史。
- `agent_contract.py:48` 的规划白名单不接受综合阶段的 `context`；`build_planning_messages()` 也没有读取历史。
- 无工具时，现代 session 在 `agentSession.ts:2123` 直接返回规划文本，因此该回答也看不到上文。
- `agentSession.ts:2063` 优先使用自身历史；CopilotKit 运行与回退交替时，较旧的回退历史可能覆盖页面传入的新历史。

**修复设计：** 规划请求新增可选的受控 `context`，复用综合阶段已有的校验规则：记忆文本最多 8,000 字符，最多 4 条历史，每条最多 1,200 字符，只接受 `user` 和 `assistant`。旧客户端省略该字段仍兼容；任意 `messages`、系统角色和客户端工具定义继续拒绝。

两条执行链均将页面本轮历史和已有安全记忆传入规划，服务端作为不可信用户上下文附加，不提升为系统指令。明确输入的商户或 ASIN 优先；唯一商户可解析“这个商户”，多个候选时澄清。纠错问题应看到原查询条件和近期回答摘要，必要时重新调用原工具核对。

本轮历史以页面传入的当前会话为准；回退 session 不得用较旧历史覆盖它。直接回答、回退和综合消费一致上下文，新对话与登出清空。原始历史仍仅在当前会话中存在。

### A5：完整月度与精简月度使用不同合并规则

线上 Shokz 的 2026-10：商户月度表点击为 0，趋势表点击为 5,697；前者仍保留 7.3% CVR。

`agentSession.ts:1097` 中普通分析请求完整接口，并使用 `mergeMerchantMonths()`；趋势请求 `minimal=1`，直接取 `monthlyAmazonMetrics`。`trendReports.ts:185` 用后来的 aggregate 行整体覆盖同月 Amazon 字段。`offer_db.py:560` 的 `sum_expr()` 在列不存在时生成 `0 AS 字段`；`format_metric_row()` 也不会保留数值空值。这样可能用占位零覆盖真实值，再保留 Amazon 旧比率。

固定响应中 Amazon 点击 5,697、aggregate 点击 0，当前普通分析返回 0，趋势返回 5,697，机制已复现。生产 aggregate 的点击列是否缺失、真实零代表何种统计含义，仍需查字段和两类响应；不能据此断言生产零一定是占位值。

**修复设计：** 共用月度字段来源与归一化规则，完整接口继续保留商品资料能力，趋势继续走轻量查询，不通过读取商品大表来获取月度数据。

实施前按以下顺序确定并测试字段口径：

1. 核对 aggregate 的列可用性与统计含义。月度输出中的缺列或空值保留为缺失，不使用占位零；改动限定在相关月度输出，不全局替换所有 `sum_expr()` 调用。
2. 点击优先对齐现有 Tier Sheet / `merchant_amazon_metrics()` 的订单点击及点击表兜底规则。若 aggregate 点击代表不同来源，分开标记，不合并成同名指标。
3. 收入、订单和总佣金依据确认后的 aggregate/Amazon 优先级合并；真实零仍可覆盖，缺失字段不可覆盖已知值。
4. EPC、CVR 和 AOV 在确定的同一月度分子、分母上计算；源比率仅在确认口径一致时引用，缺少必要输入则显示未提供。
5. 精简端点获取同样的轻量月度来源，完整与精简端点经相同归一化后输出一致指标。同步更新 Report 合并测试及权威功能说明。

### A6：组件存在，工具没有生成对应视图

`agentResultRegistry.ts` 已注册 `trend`，`AgentTrendResult.vue` 可以绘制 SVG 和切换指标。实际趋势结果在 `agentSession.ts:1722` 落入通用投影，生成 `kind=table`、`columns=[value]`，没有 `trend` 数据，组件无法被选中。

商户对比的指标嵌套在 `entities[].metrics`，通用投影仅接受一层标量，因而保留了 Tier，丢失收入、EPC 和 CVR。固定响应已复现 `columns=[tier]`。

**修复设计：** 为 `trend` 和 `merchant_comparison` 增加明确投影分支，继续复用本地 registry。趋势将 `months[].metrics` 按现有 `AgentTrendData` 契约展开，收入采用 `value`/`revenue`，指标切换仅展示实际可用指标，月份按时间正序排列。对比表显式投影商户、Tier、收入、联盟 EPC、CVR 等列，缺失字段显示未提供。

完整视图仍留在浏览器，只将受限结果送回 Python；不把 SVG、组件模板或任意 HTML 加入签名结果或模型输出。

### A7 与 A8：错误解释和正文展示没有与结果状态对齐

三个商户、12 个月和指标均已提供的请求，线上仍要求补充这些字段。`missingDataResponse()` 在 `agentSession.ts:612` 对多类失败使用同一文案。具体那轮可能是规划无调用、规划不可用或回退，现有线上现象不足以确认是哪一个。

确定性 `not_found` 被重规划的原因则可以确认：`agent_agui.py:372` 对所有失败进入第二轮；现代 session 的 `agentSession.ts:2147` 也将受控失败码纳入重规划。线上不存在的目标产生四个趋势失败结果。

**修复设计：** 复用现有受控错误和时间线，区分缺少输入、规划失败、无工具计划、目标未找到、数据不可用、部分完成和主动停止。已提供输入时不再要求重复补充；无调用的数据问题可在现有预算内纠正一次计划，仍失败则说明实际阶段和可重试操作，不能把规划文本作为具体数据事实。

`not_found`、非法过滤和非法参数作为终止类结果；仅超时或暂时不可用等可恢复错误允许有限重试。相同工具和规范参数的重复调用在签名前归一化；不能在浏览器改写签名参数。多商户任务保留明确的已完成、未完成和超预算对象，不自动扩大总预算。

正文默认给结论、关键数字、必要限制和下一步，详情表由结构化组件负责。调整当前综合提示词“必须逐月展示全部行”的要求，避免与工具表重复。来源和时间使用业务标签；`estimated=false`、`recordCount`、原始错误码等留在详情和诊断。查无结果使用简洁说明，主动停止使用“反馈本次停止”等对应文案。
